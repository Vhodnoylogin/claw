# Next steps and discrete coat variation

Owner-directed plan, 1 November 2026. Mechanisms precede physics/VR, which
precede visual polish. This plan does not publish another version.

Latest owner release sequence: first publish the FOMOD-only 0.7.0 compatibility
update, then 0.8.0 with completed mechanisms and freely selectable body families.
Finish and demonstrate discrete coat distribution afterwards as 0.8.5. The
owner rejected archive extraction as an end-user dependency installation flow;
the existing helper remains development preparation, not the proposed public UX.
Assess a complete texture bundle under the donor's actual runtime reuse terms.
The earlier private permission about excluding textures from Git applied to
repository storage; it was incorrectly generalized to every runtime archive.
The public donor instructions allow derivative texture use but also require
non-obsolescence ("no full vanilla replacer please"). A self-contained release
therefore needs that scope resolved rather than a fabricated blanket prohibition
or unrestricted grant. Colour policy and texture publication remain outside 0.8.0.

## Discrete variation using existing textures

### Treat a pattern as a complete compatible set

The inspected Elegant 2K 2.1 archive contains 34 patterns. Each has nine diffuse
maps: body, head, arms, back, belly, chest, face, shoulders and tail. Select all
nine as a unit for an actor. Preserve the existing UV layout, alpha state and
shared normal/specular/eye/mouth/claw resources. This gives actual different
markings and colours without painting a new texture or changing geometry.

Examples include Black, Brown, Ginger, Grey, Silver, Timber, White and their
authored alternatives. The full catalog also has stylized patterns such as
Hyena Spotted and Khajiit. Available does not mean automatically suitable for
every character. Keep the catalog and an allowed-pattern policy separate.

The 306 named files contain 124 unique byte payloads. For example Black ALT
retains Black's body/head but changes all seven fur maps. Silver ALT differs in
five map roles although its mean fur colour is almost equal to Silver. File
sharing does not make these the same pattern, and mean RGB alone cannot encode
their markings. Keep complete named bundles even where some files are shared.

Do not initially mix a head from one pattern, torso from another and fur from a
third. Their borders, undercoat and markings can disagree. Likewise, the nine
maps are not interchangeable independent skin/fur palettes: body/head already
contain painted coat, and material groups are not biological pixel masks.

### Keep selection separate from tint

The existing automatic rule selects the nearest measured fur colour to observed
human hair in linear RGB, with a stable ID tie-break. Explicit per-actor choices
override it. This is deterministic, but a mean colour cannot distinguish all
markings and does not guarantee that all 34 patterns will be used.

First deliver a configurable allowed-pattern list and a clear choice between
original pattern colours and pattern plus human-linked material tint. The
original-colour mode uses neutral multipliers and retains authored contrasts.
The linked mode retains the separate existing hair/skin tint mechanism. Do not
call this arbitrary recolouring: multiplicative tint cannot brighten a black
diffuse into white or produce an exact requested RGB colour.

Retain nearest-hair selection as the initial human rule. For automatic marking
variation, add explicitly authored colour-compatible pattern pools: human hair
selects the colour pool, then a stable saved per-reference choice selects its
marking variant. Do not classify compatibility solely from a filename or choose
unrelated colours just to use every pattern. Pool membership is appearance data,
not another morph matrix. Reuse the selection-origin/persistence contract below;
preserve a saved choice while it remains eligible and define source-colour
changes explicitly. Test colour families with actual sampled textures; do not
tune artistic matching in this queue.
Separate beard/brow sources remain an investigation until a real readable value
has been verified. Missing sources must not be invented.

### Cover originally-beast actors honestly

OBody body-preset inputs do not establish that a born werewolf has an observed
human hair or skin colour. Currently such actors accept explicit patterns; an
unset choice restores their existing material.

Add a separate configurable appearance fallback for actors without a usable hair
source: choose once from an allowed natural-pattern pool and preserve that
choice for the actor reference. The explicit priority is manual override, then
real readable hair selection, then this saved fallback when enabled. Skin alone
is not a hair source. Preserve genuine skin independently for linked tint even
if hair is unavailable; observed humans with unreadable hair need the same
explicit fallback/original-material policy rather than invented hair. Define
source arrival/removal and test those transitions alongside clear and reload.
Distinguish automatic fallback from explicit
override and retain existing co-save compatibility. Load-order changes, model
refresh and repeated transformations must not reroll it. Do not key solely by a
shared NPC base, which would give same-base spawns the same appearance. Do not
invent a human appearance record to make the selector run.

This is texture distribution, not random conversion matrices or a replacement
for OBody. Multiple actors may share one of 34 patterns; body morphs provide
another independent source of visible variation. Clearing an explicit override
returns to the configured automatic policy, with its origin visible in status.
The default without a prepared library remains the existing material/tint.

### Make all textures available locally

The ordinary Elegant FOMOD installation chooses one pattern; the other patterns
remain in its downloaded archive. CLAW cannot select files absent from Data.
The existing local preparation helper extracts validated pattern sets under
separate namespaced paths and writes the catalog. All 306 diffuse maps occupy
549,498,912 bytes, about 524 MiB. The library is a separate local dependency;
the single public CLAW archive remains small.

Finish and qualify the documented preparation/import path using the user's
already downloaded archive and the existing helper. An ordinary FOMOD alone
does not execute arbitrary extraction from another archive. Do not promise a
one-click installer before implementing and verifying one, or turn this into a
general MO2/tooling project. Public CLAW contains its runtime/install files and
brief usage, not foreign DDS, donor archives or developer source bundles.

The repository-only permission excludes putting donor textures in Git. Runtime
reuse has separate public conditions, including attribution and not making
Elegant obsolete. A complete self-contained bundle must satisfy that actual
scope; the repository condition alone does not establish a universal DDS ban.

## Execution order and completion criteria

1. **Close the current evidence and package slice.** Record game11's completed
   assertions and separate abnormal termination; retain independent reviews and
   restore receipts. Fix the short package README/credits and obsolete runtime
   status statements. Rebuild one minimal archive reproducibly.
2. **Finish first-queue appearance mechanics.** Add allowed-pattern policy,
   original-colour/linked-tint choice and the saved originally-beast fallback.
   Pure selection rules stay outside engine adapters. Test invalid/missing
   patterns, no library, source updates, clearing and old-save compatibility.
   Keep arbitrary colour painting, mixed-pattern seam work and artistic tuning
   outside this slice.
3. **Accept the actual installation.** Install selected final archive files,
   verify winning resources and test the projected matrices. Cover HIMBO/3BA,
   CBBE and male/female Vanilla choices in bounded scenarios; do not infer AE/VR
   acceptance from the universal build. Verify both sexes, human/wolf/return,
   born actors, same-base isolation, refresh, save/load and a normal menu exit.
   Compare native values with the same shared evaluator in Morphbench; use
   Steam images for visible coats. Investigate a reproduced exit failure from
   actual evidence, without speculative third-party fixes.
4. **Prepare the first-queue release.** Review redundancy, pure functions and
   encapsulated game/material/persistence boundaries; avoid a cosmetic rewrite.
   Recheck the current Morphbench plugin against the final shared kernel and
   external resources. Publish only the tested runtime and accurate user docs;
   released sources/test fixtures go to main, unfinished work stays in the one
   development branch. No new release is implied by this plan.
5. **Proceed to physics, then VR.** First test actual installed CBPC motion with
   active/disabled/restored comparisons; a generated configuration is not solver
   evidence. Continue provider-specific adapters, morph-responsive contacts and
   then first-person VR dispatch/visibility/synchronization. Keep existing XP32
   when possible. Visual refinement of breasts, muscles, endpoints, seams and
   self-intersections remains queue three, except actual missing-texture or
   broken-animation bugs. BHUNP remains separate planned compatibility work.
